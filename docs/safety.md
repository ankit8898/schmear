# Safety

How far a [schmear](../README.md) worker can reach, and what each vendor's terms say. Setup and routing are in the [guide](guide.md).

## Trust boundaries

There is no OS-level guarantee and no confinement. Read this before delegating.

- A worker does not inherit the driver's sandbox or permission mode. It runs under its own CLI's mode and sandbox, in any directory the driver names, so a driver limited to read-only can still get files written and commands run through `delegate`. schmear adds no sandbox and forces no mode.
- A Codex worker trusts its cwd (codex-acp marks every session root trusted), so a repository's `.codex/config.toml`, including the MCP server commands it names, takes effect without Codex's trust prompt. Delegate untrusted checkouts only to other agents, for example with `agents: ["claude", "grok", "agy"]`.
- Permission requests a worker sends are forwarded to the driver as an MCP prompt naming the worker and task. Decline, cancel, or a driver that cannot show prompts rejects that one request and the worker continues, as a headless CLI does. This is verified only in each host's headless mode (`claude -p`, `codex exec`, `grok -p`, `agy -p`), where the host cancels or declines the prompt at once; how an interactive session shows it is not yet verified. Which requests arrive is each CLI's choice: Claude and agy ask for edits in default mode, Codex only to leave its sandbox, Grok sent none for edits or MCP calls, and agy asks for every MCP call.
- Tasks given the same `cwd` share that directory. Isolate tasks that could conflict yourself, for example in separate git worktrees.
- Workers can call your MCP tools: they load the same MCP servers their CLI loads directly. Grok calls them without asking.
- schmear adds no text to the prompt and runs no git command.
- schmear strips variables that change an agent's auth or billing route from every worker's environment (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK/VERTEX/FOUNDRY/ANTHROPIC_AWS/ANTHROPIC_GOOGLE_CLOUD/MANTLE/GATEWAY`, `ANTHROPIC_AWS_API_KEY`, `ANTHROPIC_FOUNDRY_API_KEY`, `AWS_BEARER_TOKEN_BEDROCK`, `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `CODEX_API_KEY`, `MODEL_PROVIDER`, `CODEX_CONFIG`, `DEFAULT_AUTH_REQUEST`, `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_GENAI_USE_VERTEXAI`, `XAI_API_KEY`, `GROK_CODE_XAI_API_KEY`, `GROK_AUTH`, `GROK_MODELS_BASE_URL`, `GROK_XAI_API_BASE_URL`, `GROK_CLI_CHAT_PROXY_BASE_URL`), so an exported key cannot silently move a subscription run onto API credits.
- schmear never writes or refreshes a CLI's login token and never runs inference to read usage. It reads these credentials in memory only. The Claude, Codex and Antigravity ones are read only when that agent's own CLI usage read has failed:
  - The Claude Code OAuth token, from `$CLAUDE_CONFIG_DIR/.credentials.json` or `~/.claude/.credentials.json`, or on macOS, for the default login only, from the Keychain item "Claude Code-credentials" through `/usr/bin/security`. It is sent only to `api.anthropic.com` for a read-only GET of `/api/oauth/usage`, as Claude Code's own client, with Claude Code's `claude-cli/<version> (external, cli)` User-Agent. An expired token is not refreshed: `claude` refreshes its own.
  - The Codex login in `${CODEX_HOME:-~/.codex}/auth.json`: a personal access token (`personal_access_token`), sent only to `auth.openai.com` and `chatgpt.com`, and the OAuth access token, sent only to `chatgpt.com`, both for read-only GETs of usage. The personal access token request carries Codex CLI's `codex_cli_rs/<version> (<os> <version>; <arch>)` User-Agent and `originator: codex_cli_rs`; the OAuth request says `schmear/<version>`.
  - The Antigravity app's local-server token, read from the process list (`ps`), sent only to `127.0.0.1` for a read-only quota call. It applies to the default login only and never appears in output.
  - The Grok login token in `~/.grok/auth.json`, for Grok's usage fallbacks.
- Credit pools use three more kinds of credential, all set up only in `schmear credits` and `schmear credits login`. None of them is ever printed, logged or put in an error, and a prompt's error never quotes your reply, so a header piped into the wrong prompt is not echoed.
  - A Claude Console session: the `sessionKey` cookie when imported, the whole `Cookie` header when pasted with `--stdin`. It is stored with mode `0600` in `~/.config/schmear/console-sessions.json` (directory `0700`), only as one line of printable ASCII, and removed by `schmear credits logout` or `schmear uninstall`. It is a full Console session that can create API keys and buy credits. schmear sends it only to `platform.claude.com`, with redirects disabled, for read-only GETs of the undocumented `/api/organizations`, `/api/organizations/<org>/prepaid/credits` and `/api/organizations/<org>/current_spend` (this month's spend, shown in `usage`; a failed spend read changes nothing).
  - A Google session: every first-party cookie on path `/` that applies to `me.developers.google.com` when imported, the whole `Cookie` header when pasted. It is stored the same way in `~/.config/schmear/google-sessions.json`. It is a full Google account session; schmear sends it only to `me.developers.google.com`, in a GET and a read-only `batchexecute` POST per signed-in account per read (plus one GET that finds no further account), on undocumented endpoints that may change (the same read CodexBar's googledeveloper provider makes).
  - Each credit pool's API key. You paste it at a hidden prompt. A value that does not look like a key (`sk-ant-api…`, or `AIza…`/`AQ.…`) is sent nowhere. A key that does is checked with one request: `GET api.anthropic.com/v1/models` with `x-api-key`, where the response's `anthropic-organization-id` must equal the org's id, or `GET generativelanguage.googleapis.com/v1beta/models` with `x-goog-api-key`. After your typed `yes`, schmear writes it through the stdin of `/usr/bin/security -i` into your login Keychain (macOS) or of `secret-tool store` into your keyring (Linux), as account `schmear`, service `schmear-anthropic-<name>` or `schmear-gemini-<name>`, then reads it back to prove the store. schmear never puts the key in argv, a URL or a file. The pool's `keyCommand` reads it once per task (`/usr/bin/security find-generic-password -s <service> -a schmear -w`, or `secret-tool lookup service <service> account schmear`), without a shell and with a 15 s timeout; `schmear credits status` runs it too. A Claude pool's key goes to the worker in `ANTHROPIC_API_KEY`, a Gemini pool's in `GEMINI_API_KEY`, in that spawn's environment only; commands the worker runs inherit it. A failed read records only its error in `~/.local/state/schmear/key-errors/<pool id>.json`. A stored key is shape-checked again before schmear offers to reuse it.
- `schmear credits remove <id>` and `schmear uninstall` delete only a key schmear stored: the Keychain or keyring item of account `schmear` and the pool's own service, and only when the pool's `keyCommand` is exactly schmear's read command. A key read by a `keyCommand` you wrote is left alone. A deleted key still works at the vendor until you revoke it there.
- Browser import runs only when you pick "Import it from my browser" in `schmear credits` or `schmear credits login <claude|google>`; paste is the default answer, also for piped input. `schmear init`'s subscription setup, `usage`, `serve`, `delegate`, routing and the apps never read a browser; `init` reaches the import only through its "Set up API credits now?" offer and that same choice. The import:
  - reads the cookie files of every profile of the listed browsers (macOS: Chrome, Chrome Beta, Chrome Canary, Arc, Brave, Edge, Chromium, Vivaldi, Dia, Firefox, Zen; Linux: Chrome, Chromium, Brave, Edge, Firefox). Safari is not read. Each cookie database, with its `-wal` and `-journal`, is copied into a `0700` directory under `~/.local/state/schmear/tmp`, one at a time, with no prompt or network call while the copy exists, and deleted after. A run killed mid-read can leave that one copy, readable only by you;
  - selects only rows of the vendor's own hosts and decrypts only those. A row whose name is not a valid cookie name or whose value is not printable ASCII is dropped;
  - for a Chromium browser, reads the browser's cookie key: on macOS its "Safe Storage" Keychain item through `/usr/bin/security find-generic-password -w`, for which macOS asks for your login password; on Linux through `secret-tool lookup`, which may ask to unlock your keyring. The key stays in memory for that run. **Allow** is enough. **Always Allow** lets any program you run read that browser's cookie key without asking, and with it decrypt every cookie of that browser.
  - Corporate endpoint security (EDR) may flag `security find-generic-password -w` as credential access. On a managed Mac, paste the header instead.
- Claude credit pools: schmear reads each org's auto-reload setting on every balance read and skips the org unless the setting reads as off; a setting it does not recognize counts as on. The wizard refuses such an org.
- Network: `schmear serve` is a stdio MCP server, opens no port and sends no telemetry. schmear itself contacts only `api.anthropic.com` (Claude usage, and the check of an Anthropic key you paste), `auth.openai.com` and `chatgpt.com` (Codex usage), `grok.com` and `cli-chat-proxy.grok.com` (Grok usage), `127.0.0.1` (the Antigravity app's local server), `platform.claude.com` (when you store a Claude Console session for credit balances), `me.developers.google.com` (when you store a Google session) and `generativelanguage.googleapis.com` (the check of a Gemini key you paste; credit runs reach the Gemini API through `agy`); everything else goes through your own CLIs. The Claude, Codex and Antigravity credential reads happen only after the agent's own CLI usage read fails.
- Environment: workers inherit schmear's environment except the stripped variables above (`workerEnv` in `src/acp.ts`), so tokens such as `GITHUB_TOKEN` or cloud credentials in that environment reach every worker.
- Gemini credit runs start `agy acp --gemini-dir <own home>` under the data dir, so they skip your `agy` settings, MCP servers and skills. The saved Antigravity login is in the macOS keyring, which that home does not isolate; isolation from it rests on the mandatory key-mode `authenticate`, and any failure of it fails the run before a session opens.
- Gemini credits: schmear cannot see the AI Studio prepaid balance, and one run has no spend limit, so a run can spend past the credit into that balance until Google stops at zero (HTTP 402). Keep the balance small and auto-reload off. Google documents that credits are spent before prepaid funds; schmear has not verified this, since no credit holder has run the check.
- A worker's own `schmear serve` (started from its MCP config) sees `SCHMEAR_WORKER=1` and exposes only `usage`. This prevents accidental delegation loops; it is not a security boundary, since a worker with a shell can unset the variable or run another CLI directly.

## Parity

Workers have the default tools, MCP servers, skills and plugins their CLI has when run directly in the same directory. Differences found by the parity test, all from the CLI's own behavior:

- The stripped variables, and the model and effort schmear sets.
- Claude: MCP servers can still be `pending` at the first turn; the SDK entrypoint omits one built-in plugin and adds `SendToProject`; `EnterPlanMode`/`ExitPlanMode` are missing and `AskUserQuestion` is disallowed (as in Claude Code's own subagents).
- Codex: codex-acp disables the `visualize` skill, trusts the session root (see above), and turns off `cwd_relative_turn_diffs`. schmear sets the codex-acp mode that matches your Codex config.

## Terms of service

Sources were read on 2026-11-22. schmear does not decide whether a vendor's terms cover your use; read them yourself.

- **Anthropic.** The [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview) says "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products", including Agent SDK agents. The [Legal and compliance page](https://code.claude.com/docs/en/legal-and-compliance) says Anthropic "does not permit third-party developers to … route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users", and may enforce this without prior notice. The same page says this does not "prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription". schmear runs your unmodified `claude` binary on your own login. If `claude`'s own usage read fails, schmear also reads Claude Code's OAuth token (the credentials file, or the macOS Keychain item through `/usr/bin/security`) and sends it only to `api.anthropic.com/api/oauth/usage` for a read-only GET with Claude Code's own User-Agent, as CodexBar does; it makes no model request and never refreshes the token. No Anthropic statement on usage reads like this was found, and Anthropic does not say whether a tool you run for yourself falls under the first two statements or the carve-out. When you configure Claude credit pools, schmear stores your Console session cookie and calls undocumented `platform.claude.com/api/...` endpoints read-only outside Anthropic's clients; no Anthropic statement on this was found, and these endpoints may change or be restricted.
- **Anthropic, billing.** On 2026-04-04 Anthropic moved third-party harnesses, starting with OpenClaw, to separately billed extra usage, saying the policy "applies to all third-party harnesses" ([TechCrunch](https://techcrunch.com/2026/04/04/anthropic-says-claude-code-subscribers-will-need-to-pay-extra-for-openclaw-support/)). A planned change to Agent SDK billing was paused on 2026-06-15; Agent SDK usage on a plan "still draw[s] from your subscription limits" ([help center](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)).
- **Google.** The Antigravity [FAQ](https://antigravity.google/docs/faq) (read 2026-11-24) says that "Wrapping `agy` inside third-party coding agents or applications" is not supported on consumer plans, and names automated account rotation in the same sentence; the [terms](https://antigravity.google/terms) treat third-party access as possible grounds for suspension. schmear is such a wrapper: another vendor's agent drives `agy acp` through it, and with two Google accounts it picks between them. Google documents [`agy acp`](https://antigravity.google/docs/cli/acp) for editors' chat panels only. Users reported accounts disabled after signing in through OpenClaw ([openclaw#14203](https://github.com/openclaw/openclaw/issues/14203)), which extracted tokens; schmear does not extract or use a Google token. For the default login, if `agy`'s own usage read fails, it reads the running Antigravity app's local-server token from the process list and sends one read-only quota request to that server on `127.0.0.1`; no request leaves your machine, and no Google statement on this was found. The account at risk is your Google account. Antigravity is unticked in the `schmear init` checklist until you tick it.
- **xAI.** xAI's [Grok Build announcement](https://x.ai/news/grok-build-cli) advertises ACP support for building your own agent orchestration apps; schmear's Grok workers use `grok agent stdio` over ACP. Its Grok usage fallbacks read your Grok login token and call grok.com endpoints with it, read-only, outside the Grok client; no xAI statement on this was found.
- **OpenAI.** schmear runs the official `codex` CLI on your own login. If `codex`'s own usage read fails, schmear also reads the personal access token or OAuth access token in Codex's `auth.json` and sends it, read-only, to `auth.openai.com` and `chatgpt.com/backend-api/wham/usage` (the personal access token with Codex CLI's User-Agent and `originator`, the OAuth token as `schmear`), without a model request or a refresh. No OpenAI statement on usage reads like this was found.
- **Several accounts.** schmear can route to more than one login per provider ([Accounts](guide.md#accounts)). A provider's consumer terms may limit how one person uses several of its subscriptions; read them before adding an account.

## Claude disclosure

Claude workers run your own `claude` binary on your claude.ai login through Anthropic's Agent SDK, without the adapter's `--hide-claude-auth` flag. Anthropic restricts third-party use of subscription logins and may restrict your account or this route. The adapter is `@agentclientprotocol/claude-agent-acp`; its `--hide-claude-auth` flag would refuse subscription billing. Anthropic's statements are quoted under [Terms of service](#terms-of-service).

To avoid the risk, untick Claude in the `schmear init` checklist; the other three providers keep working, and later runs keep Claude unticked.

If Claude's extra usage is on, a task that crosses the limit may bill your card. schmear cancels a task as soon as Claude reports overage but cannot stop the request in flight.

The Claude route installs `@anthropic-ai/claude-agent-sdk`, a dependency of `@agentclientprotocol/claude-agent-acp`. Its `license` field is `SEE LICENSE IN README.md`, and that README points to Anthropic's Commercial Terms of Service, not an open-source license. It is installed whenever Claude or Codex is ticked, so declining Claude alone does not avoid it.
