# schmear on MCP 2026-07-28

Researched 2026-11-24. Nothing here is built; spec §12 "Protocol revision" and §18 point at this note.

## Recommendation

**No protocol change now, and none is needed before 1.0.** schmear's server (`@modelcontextprotocol/sdk` 1.32.2) is legacy-only. Every host that tries 2026-07-28 first is dual-era and falls back to `initialize` (spec compatibility matrix, "Dual-era | Legacy → Works"), which keeps both Decisions true today (R8, R31). If schmear went dual-era (SDK v2), Claude Code would pick modern, and permission forwarding would rest on host MRTR behavior nobody has measured.

**Trigger:** move when (a) a host stops falling back for stdio servers; (b) a needed fix lands only in SDK v2 (v1.x fixes are promised only until about 2027-01-27); or (c) the owner chooses.

**SDK plan.** At the trigger, move in one change from `@modelcontextprotocol/sdk` ^1.32.2 to `@modelcontextprotocol/server` ^2.4.0 (stable since 2.0.0, 2026-07-27), using `serveStdio(factory)`, which serves both eras by default. The tasks extension is not used: SDK 2.4.0 has no server support for it, only Claude Code is known to support it, and it would make `delegate` run in the background.

**Open ruling.** A `serve --driver <id>` flag, written by init per host, would identify the driver without the handshake (`clientInfo` becomes an optional per-request field that servers "SHOULD NOT" act on). It needs the owner to re-rule the Decision "The driver is identified from the MCP handshake `clientInfo`"; until then phase 2 reads `clientInfo` from each request's `_meta`.

**Main unresolved uncertainty:** whether each host's MRTR client caps rounds per call or times each round separately. The v2 client defaults to 10 rounds and Claude Code runs it; a 50-task batch can need more than 10 prompt rounds. Only the owner-run probe below settles it, and its answer decides phase 2.

## Phase 2 design (built at the trigger)

**Shape.** Swap `@modelcontextprotocol/sdk` for `@modelcontextprotocol/server` ^2.4.0, and add `@modelcontextprotocol/client` ^2.4.0 as a devDependency. `serveStdio(() => createServer(adapters), {})` keeps the `legacy: 'serve'` default, so legacy hosts get today's behaviour from the same factory. Shutdown and close stay on the returned handle. `delegate.ts`, `permit.ts` and `Ask` do not change: only the `ask` passed in differs by era.

- **Legacy-era call:** today's handler. `ask` is the push `elicitInput` with a 24 h timeout.
- **Modern-era call** (the request carries the `_meta` envelope):
  - The driver is the `clientInfo` name from the request envelope (a `--driver` flag, if the owner re-rules it, takes precedence).
  - Form capability is read from the request's `clientCapabilities`; a bare `elicitation: {}` counts as form.
  - The handler goes through a batch registry, new in `src/rounds.ts`:
    ```ts
    export interface Prompt { message: string; options: PermissionOption[] }
    export type Step = { kind: "done"; results: TaskResult[] } | { kind: "input"; prompts: Record<string, Prompt> };
    export interface Batch {
      readonly id: string;                                 // randomUUID(); sent as requestState
      answer(responses: Record<string, unknown>): void;    // accept + string content.option → that id; any other entry → undefined; unknown or closed keys ignored
      next(signal: AbortSignal): Promise<Step>;            // open prompts → input at once; else waits for a prompt or the run; rejects with the run's error
    }
    export function openBatch(start: (ask: Ask, signal: AbortSignal) => Promise<TaskResult[]>, detachMs: number, onEnd: () => void): Batch;
    ```
- **Handler flow, modern era:**
  - No `requestState`: open a batch whose `start` runs `delegate(args, {driver, signal: AbortSignal.any([batchSignal, shutdown]), ask: formCapable ? ask : undefined})`, and store it in `Map<id, Batch>`.
  - With `requestState`: look the batch up and pass `ctx.mcpReq.inputResponses ?? {}` to `answer`.
  - Then `step = await batch.next(ctx.mcpReq.signal)`.
  - On `done`, return today's text result, then `onEnd` drops the batch.
  - On `input`, return `inputRequired({inputRequests: {<key>: inputRequired.elicit(<today's form params>)}, requestState: batch.id})`.
  - The batch's run promise stays in `activeCalls` from start to `onEnd`, so shutdown still waits for workers.
- **Prompt lifecycle:**
  - `ask` registers key `q<n>` and resolves on `answer`.
  - When its `turn` signal aborts, the key is removed and the prompt resolves `undefined`. A later answer for that key is ignored; MRTR has no way to withdraw a prompt the host is already showing.
  - Every input step carries all open keys, so a key missing from a retry is asked again, as the MRTR spec says it SHOULD be.
- **Detach:**
  - Returning an input step starts a timer of `detachMs = 86_400_000`; `next` clears it.
  - When the timer fires, the batch aborts (every worker cancelled, final `cancelled` lines in `tasks.jsonl`) and is dropped. That matches today's 24 h host timeout; no request could ever receive the results.
  - If the run finishes while the batch is detached, the results are held for the next retry.
- **Cancel:** `notifications/cancelled` for the attached round aborts the batch, as §10 step 9 does. While detached there is no request to cancel; abandonment ends at the 24 h timer, or at stdin close when the host session ends.
- **Errors:**
  - A `requestState` with no batch gives the tool error `delegate: no running call for this retry (schmear restarted, or 24 h passed without a retry); its workers were stopped`.
  - A second request attaching to an already attached batch gives the tool error `delegate: this call is already waiting for an answer`.
  - Validation errors thrown by `delegate` reject `next`, so they reach the host as a tool error, as today.
- **Integrity:** `requestState` is a random 122-bit id held only in this process. An altered or forged value finds no batch and fails the request, the case where the spec allows omitting HMAC. Retry arguments are ignored, because the batch already holds its tasks.
- **Blocking semantics hold.** The host's client runs the rounds inside one tool call (v2 client `callTool` auto-fulfil), so §2 "A blocking `delegate`" stays true.
- **Tests:**
  - `test/server.test.ts` runs its suite in two `describe` blocks, `versionNegotiation` `{mode: "legacy"}` and `{mode: "auto"}`, both over the SDK's `InMemoryTransport` through `serveStdio(factory, {transport})`. The existing elicitation tests must pass unchanged in both, because the v2 client fulfils MRTR through the same `elicitation/create` handler.
  - New `test/rounds.test.ts`, using `mock.timers` from `node:test`, covers: two prompts open at once arrive in one step; a retry missing one key re-asks only that key; an unknown id gives the tool error; the detach timer cancels the workers; cancelling the attached round cancels the workers; a run that finishes while detached completes on the next retry.
  - `test/serve.test.ts` checks that the spawned `serve` answers both `initialize` and `server/discover`.
- **Spec at phase 2:** §4 diagram line becomes `MCP stdio: initialize(clientInfo) or per-request _meta → tools/call delegate | usage; ← elicitation/create, or input_required rounds (worker prompts)`; §12 "Permission prompts" gains the modern-era sentence and the detach rule; §12 "Protocol revision" is rewritten to say schmear is dual-era; the §18 line is deleted; a new R entry records the probe.
- **Conditional:** if the probe shows a round cap below `maxTasks`, stop before building and take the owner's ruling: (a) prompts past the cap are rejected, as for a driver without elicitation, and the worker continues; (b) the tasks extension is used on that host; (c) keep legacy by staying on v1 for as long as the host falls back. The Decision "Permission prompts are forwarded … over MCP elicitation" stays true under MRTR: the prompts are still form elicitations, now embedded in the result.

## Deferred

- Coalescing prompts that arrive within a short window into one round; only if the probe shows round caps matter and batching would fit under them.
- The tasks extension for Claude Code (questions held in `/tasks`, no round cap); revisit when `@modelcontextprotocol/server` ships server support.
- An `elicitation.url` fallback for a host without form elicitation: none of the four lacks it (R31).
